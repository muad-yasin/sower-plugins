# LLM failure modes in 3D authoring

*Open this file before a first DCC session, before any batched build, and whenever an agent is about to author geometry from computed coordinates. `SKILL.md` states the headline; this file names each failure family and its counter.*

**Grades.** **D** = documented in a named source, read on the date given. **I** = inferred, with the reason in the sentence.

## What the benchmarks report

Each benchmark below tests general code generation for 3D, not any particular tool setup: carry the direction of its finding to your pipeline, not its numbers (I).

- **P3D-Bench** (arXiv 2606.11152, version 4 of 14 October 2026; its summary of findings read 2026-11-22): models often recover an object's overall shape and identity yet fail to reproduce the parametric geometry the input specifies. In its summary, the strongest model tested scored about 0.7 on a model judge's semantic alignment and about 0.5 on geometric alignment (D).
- **3D-PreMise** (arXiv 2401.06437, 2024; its error analysis read 2026-11-22): in its analysis of GPT-4's failed cases, sampled at temperature 0.9, spatial precision errors, slight deviations in position, scale or rotation, were the most frequent category. At the level of the program, defining the parameters a prompt gives as variables in the code lowered the parametric error rate (D).
- **3DCodeBench** (arXiv 2606.01057, abstract read 2026-11-22): failures "mostly arise from API mismatches, while successful renders still suffer from disconnected or floating 3D geometric components", and test-time scaling, higher thinking budgets and refinement over several turns, improves performance overall (D).
- **BlenderGym** (arXiv 2504.01786, CVPR 2025, abstract read 2026-11-22): even the state-of-the-art vision-language system "struggles with tasks relatively easy for human Blender users", and inference compute "can be optimized by strategically distributing it between generation and verification" (D). The build, check and duplicate loop of `SKILL.md` is that split (I).

## The named families, each with its counter

- **Spatial precision: never trust authored numbers without a render.** Coordinates that agree with each other in the script are no evidence that the shape is right (I, from the findings above), and they feel trustworthy from the inside because they were computed, not guessed (I). A verification round trip skipped to save time is paid back in rework. Counter: render, measure the bounds, and compare against the spec, every time; and, after 3D-PreMise, put the dimensions a spec gives into named variables in the script (I).
- **A rotation tool does not rescue spatial reasoning.** A multimodal model given a module that renders and rotates 3D models reached at most 62.5% accuracy on rotation tasks (D, arXiv 2603.26779, version 2 of 31 May 2026, abstract read 2026-11-22). For any rotation or offset beyond one move along an axis, use the temporary pivot (`unity.md`) or let the engine compose the transform, and **verify the result, never the mental model** (I).
- **API version drift.** Recall runs to older releases' conventions: renamed properties, moved enums, wrong module imports, each an attribute error on an API that was once real (not checked at a source; stated here since September 2026). Counters: **pin the version in the context**, the release and its Python API; check recalled names against a committed script known to run on the installed binary; and **on a crash, feed the real traceback into the next attempt**, which is the refinement over several turns that 3DCodeBench found to improve performance (D, above).
- **Axis and coordinate-system confusion is a named family, not an occasional slip** (I). Blender uses Y forward and Z up, and for an application with Y up its manual names -Z forward and Y up (D, Blender 5.3 manual, "FBX (Legacy)", read 2026-11-22); an exporter and an importer that both convert, or neither, give a rotated import (I). The counters are structural, not vigilance: **one fixed export flag set, never improvised per export** (`blender-authoring.md`); the convention stated at the top of the script ("every Z in this script is the game's Y"); and **an orientation check in the render after import, before anything is built on top.**
- **Destructive operations go to exact, listed names.** An instruction like "clean up the extras" leaves the target set implicit, and an agent can delete the wrong object (not checked at a source; stated here since September 2026). **List the targets by name and check the list against the live scene before executing**, and in a live DCC session **save first**: undo across bridge operations is unreliable (not checked at a source; stated here since September 2026). Consistent object names are what make lookups by name safe at all (I).
- **Node-graph recall is thin.** Visual node graphs are sparse in training data and have changed incompatibly between major versions, so a confident graph can hold deprecated nodes or wrong socket types (not checked at a source; stated here since September 2026). If a node-graph pipeline is proposed, **this weakness is part of its cost** (I).
- **Batch scripts print a summary per object**: its name, its triangle count and the file written. A headless run that half-fails can exit 0 and pass silently, and one line per object is the cheapest instrument against it (I). The engine side has the same rule: read the console after every mesh or material call.
- **Tool-bridge specifics**: an object referenced that does not exist (list before you mutate), the wrong editor instance when more than one is open (pin the instance first), and operations landing in a live play session, which is the Play Mode trap of `unity.md` in another form (I).
