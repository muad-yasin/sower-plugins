# Timing, lifecycle, layout and verification

*Open this file before you verify interface work live, before you wire anything shaped by a camera, a hotspot or a lifecycle, before you reopen a settled layout choice, and whenever a check passes in a way that feels too easy: most entries here exist because a signal that looked obvious was wrong.*

**Grades.** **Seen** = it happened on the source project, with its record named in `evidence.md`. **D** = documented in a named source, read on the date given. **I** = inferred, with the reason in the sentence.

## 0. Designing away the bug class: where the idea comes from, and where it stops

`SKILL.md` states the rule, the order of the three answers and the limit; this is the lineage and what the source project's two cases add.

- **The lineage.** "Make illegal states unrepresentable" is Yaron Minsky's phrase, from his talks and writing on effective ML (D, Jane Street's blog, "Effective ML Revisited", 9 March 2011, read 2026-11-22). Richard Feldman's elm-conf talk of 2016, "Making Impossible States Impossible", carries it to front-end code (not checked at a source; stated here since September 2026), and Alexis King's "Parse, don't validate" (5 November 2019, read 2026-11-22) gives it a method: a parser turns less-structured input into more-structured output, so what a check learned is kept in the type instead of thrown away (D). One idea in three wordings: instead of checking at every use that a value is sane, shape the type or the interface so that an insane value cannot be built.
- **The two cases, and the harder lesson.** On the source project a hide-list made "two screens shown at once" representable; the navigation stack made it unwritable, because pushing is the only way to show a screen and the stack owns hiding (Seen; `unity.md`, "Navigation"). The shared formatters are the other case, and the harder one: the culture class reached the project five times by August 2026, and the last two came after the formatters existed (Seen). A good route that stays optional does not make the bad one unrepresentable: close the bad route too, with a guard that fails the build on a raw format call (I).
- **The counter-argument.** Taken far enough, hard constraints make a model brittle, and a state the product later wants costs a refactor instead of an `if` (not checked at a source; stated here since September 2026, after a blog post by Sean Goedecke). The limit in `SKILL.md` follows from it: constrain the states that have actually bitten.

## 1. Peer references and timing

- **A covered camera still renders:** every enabled camera renders every frame, whatever covers its output. `SKILL.md` has the disable that did nothing before its reference resolved. An audit on the source project found a second shape on 3 September 2026: a screen that starts active had its room camera enabled from startup, and nothing disabled it until the first push of the navigation stack, so on every fresh install the room rendered behind the intro dialogue's opaque overlay for as long as the player read it (Seen). Check which cameras are on at startup, not only what happens on hide.
- **Verify an editor operation's output on disk, never its log.** Grep the saved artifact for a value only the new code writes, check its timestamp against a marker, or read the changed field back (Seen: the source project's standing rule). The log lies in two ways. One is the stale-assembly run of `unity.md`, "Editor builder scripts": the log does not say which code ran. The other is *partial-write staleness*: a tool that really ran can skip fields by design. On the source project a bake that copied into an existing asset never touched its hand-tunable fields, so a changed default re-baked "successfully" while the live asset kept the old value (Seen).
- **Edits made during a live play session revert when it stops:** Unity never writes play-mode changes back to the saved scene (Seen: the source project's records; `SKILL.md` has the count). The first case cost several verification passes, because the moved desk's tap hotspot had been created in edit mode and never moved, which hid the desk's own drift; the second was caught only because the camera's position was queried again right after play mode stopped (Seen). Iterate live as much as you like; then redo the final value as a deliberate edit, save it, and verify again from a fresh session.
- **Activation:** `SKILL.md` has the rule and the case. A placeholder string in a verification result means "too early", not "wrong wiring" (Seen: the source project's decision log). In production code, a handler on a persistent object that can run before its own `Start()` has run resolves its peers at the point of use (I).
- **A scripted trigger that has to coordinate with a system's own output registers its intent, then polls a may-fire gate**; it never fires the moment its condition is due. The system holds its own output while any scripted beat is pending, so the beat is guaranteed to come next and two due beats come one after the other. The pending flag is count-based: each instance balances its own set and clear, the count is floored at zero, and teardown releases it (Seen: the source project's news plan of July 2026, as its earlier skill names the built shape). Two failure modes. A hold that is never released stops the system's output for good: on the source project a debug skip left the news feed's pacing freeze on and silenced the feed for the rest of the session, found and fixed on 22 September 2026 (Seen). And an unbalanced clear releases another instance's claim (I).

## 2. Five settled layout choices, and what each rests on

`SKILL.md` rule 6 says to follow settled patterns; this is why these five are not open questions.

- **(a) A shell filled once, or rows destroyed and rebuilt.** On the source project one list shipped as a shell filled once, on the assumption that its roster was fixed; the roster grew, the shell could not show the new set, and the pattern had to be swapped wholesale instead of extended (Seen: its earlier skill names the case). The rule is about what the shell can represent, not about performance: if the set can change at runtime, a shell that can be filled only once is the wrong shape at any size.
- **(b) No horizontal layout group on a simple two-element row:** anchor both elements directly, which is deterministic and shorter. The source project's earlier skill calls a horizontal group that mixes fixed and flexible children its proven-unsafe shape, without naming a case, and says nested vertical groups never showed the failure (I). Direct anchoring is also what fixed the second case of (d), whose rows were horizontal groups (Seen).
- **(c) A fixed layout group that compresses its children.** When an optional child pushes the content past the screen's height, a plain fixed group neither scrolls nor clips: it gives the children less than they ask for, so the symptom shows on elements nobody touched (I). A scroll shell with a content-size fitter is the fix, and it has to be there before the growable child exists. On the source project an audit of 1 August 2026 found the one panel of three that lacked the shell its two siblings had: at 16:9 the screen needed 1,777 px of the 1,620 it had, and each of its four text blocks got 11 to 20 px less than its line box asked for; how much of that showed was not settled, and the fix gave the panel the shell (Seen).
- **(d) Pass zero flexibility explicitly on a region that holds a nested force-expand group.** Otherwise its parent treats it as fully flexible: left unset, the region's flexible height falls through to the nested group's own value of 1 (Seen). On the source project a header and a controls row meant as small fixed regions each took about a third of the screen until `flexibleHeight: 0` was passed on both; later, rows built with horizontal groups gave a card a flexible height of 3, and it stretched from 250 px to 798 px and put a button on top of it (Seen). Confirm with `LayoutUtility.GetFlexibleHeight()`: a screenshot cannot tell "correct" from "correct at this one aspect".
- **(e) An overflow effect inside a masked container** is clipped with no warning: `SKILL.md` rule 9 has the rule and the case. The exception by construction is an effect drawn on an overlay that is always the topmost sibling and positioned by projecting the target's world corners into the overlay's own space: no mask above the target can clip it (Seen: the source project's tutorial halo, as an audit of 10 August 2026 confirmed).

## 3. Verifying that text actually rendered

On the source project one chain of false signals cost two wrong diagnoses in a day (Seen, July 2026):

- **A text component's mesh vertex count is not a sign that it drew.** A header known to be good, confirmed by screenshot, reported 4 vertices for its overline and heading, because uGUI text goes through the canvas renderer, not that mesh. Two hypotheses were chased off this number before it was checked against that control (Seen).
- **A garbage negative width from `GetRenderedValues()` means "never laid out yet"**, a matter of frame timing, not a defect (Seen: the same record).
- **A screenshot beats both** when the question is whether the text drew.
- **A hand-rolled screen header did not render where the shared header helper does,** and the difference responsible was never isolated (Seen). Use the helper, and find its children by name when a caller needs them.
- **An atlas whose sampling point size does not match the rendered sizes gives artifacts, not errors:** letters inside faint translucent boxes, with padding the usual second cause (not checked at a source; stated here since September 2026). If text renders slightly wrong rather than not at all, suspect the atlas before the layout. It is one more reason for one shared font asset and material preset (`unity.md`, "Canvas performance").

## 4. Why you cannot self-certify UI: the evidence, graded

`SKILL.md` states the study's headline. This is the sourcing, kept because the strength of the evidence differs from item to item.

- **Accessibility and colour alone (D: peer-reviewed; read 2026-10-04 in an earlier research round of ours, not again for this file).** "Generated Inaccessible: Measuring WCAG Violations in AI UI Design Tools", Web for All conference (W4A) 2026: 54 designers, six AI UI design tools, 21,880 assessments over five WCAG criteria; overall compliance 29.0%, contrast 26.8%, use of colour 19.2%; and asking for accessibility in the prompt *lowered* compliance. It measured design generators, not code-writing agents: a prior for an agent like you, not a finding about it. Whether colour carries meaning alone is among the most mechanical of those criteria to check, which is what makes 19.2% the figure to remember (I). The control is a structural pairing (every colour-coded state also sets a sign, an icon or a shape) and a computed check afterwards (§5, item 3). A case study of GPT-4o found its default web code often short of WCAG, and found that screenshots given with the prompts helped it choose contrast colours (D, arXiv 2501.03572, version 2 of July 2025, abstract read 2026-11-22).
- **Happy-path bias (D: a preprint).** A study of four code models on the CoderEval benchmark found 35.2% of their outputs less robust than human-written code, with over 90% of the deficiencies caused by missing conditional checks (D, arXiv 2503.20197, version 4 of September 2025, abstract read 2026-11-22). That is the reason behind the all-states rule, and the state most likely to be skipped is the one a request does not describe (I).
- **Culture-sensitive parsing (Seen).** The source project's own count is the evidence: five occurrences by August 2026 (`SKILL.md`, "Data binding").
- **Shortcuts in verification (D: a preprint).** EvilGenie, a benchmark of 154 hard LiveCodeBench problems, ran Codex, Claude Code and Gemini CLI. On its 145 unambiguous problems they hard-coded outputs in 0.7%, 2.1% and 0% of cases, in that order; on its 9 ambiguous ones the three rates were 44%, 33% and 22%, which our reading did not assign to the agents (read 2026-10-02 in an earlier research round of ours, from the full text). Its abstract reports explicit reward hacking by Codex and Claude Code (arXiv 2511.21654, abstract read 2026-11-22). Nine problems is a small sample, so take the rates as a warning, not as a rate for your project. The local reading: on an ambiguous "make it work", the cheapest passing signal is the tempting one (I).
- **Layout by magic numbers (I).** That generated UI bolts on ad hoc constants instead of measured constraints is plausible and matches the wrapping-text history ("a bigger constant is not the fix"), but it rests on practitioners' reports, not a study. A prior, not a finding.

## 5. The verification protocol that needs no device

An agent cannot certify by inspection that a screen looks right, but it can write and run checks that answer specific deterministic questions; name what stays unverified instead of papering over it. An item marked *proposal* has a real setup cost: raise it before adopting it, and never write as if it were existing practice.

1. **All states rendered.** For each data-bound screen, drive every state on `ux-design`'s list that the screen can reach, and confirm that each one renders. Where this is done by hand, that is the gap, not the rule.
2. **Real input, not invoked handlers** *(a proposal where not installed)*. A test fixture can drive input from code with no hardware; a raycaster query with a constructed pointer event exercises the real hit path. **An invoked handler never exercises hit-testing**, so it cannot catch an element that is visible but not clickable: a wrong raycast target, an overlay in the way, the wrong sibling order. Cost: a test assembly, and the frame boundary of `SKILL.md`'s timing section.
3. **Accessibility checks by computation, with no framework.** Contrast between two opaque colours is fully determined by their values: compute it against the ratios `ux-design` sets, never judge it by eye, and with a small fixed palette one pass over its opaque pairs covers every screen. A colour that is translucent, tinted or blended, or text over an image, has no stored pair: take that pair from a capture of the state in question, which is `visual-craft`'s rule, with the case behind it. Target minimums read straight off the element's rect. **Colour alone is checkable by structure:** does every colour-coded state also set a sign, an icon or a shape? Cost: close to none, a test over the palette constants and a walk over the prefabs. Given §4's 19.2%, do not skip it.
4. **Multi-shape capture assertions.** On the source project every capture harness rendered only the design reference canvas, the one shape where a screen's surplus height is zero, so the whole tool layer was blind to any defect that appears only when there is surplus: that is how the hole of about 450 units survived six visual passes and a conformance sweep (Seen). Own **four named shapes** and let each harness take the one that suits its job: the design floor (compression and overflow, the short extreme); **what people actually hold** (the default for anything a person reads); the tall ceiling (the most surplus, for machine sweeps); and a split-screen or wide shape (the only one that runs the wider-than-design branch and the cap on design width, so it covers tablets too). A shape in between adds no bug class: slack defects grow with the surplus, so the ceiling covers the range (Seen: the project considered such a shape and dropped it for that reason).

   **Two traps, both paid for** (Seen). (1) An overlay canvas is sized by the editor's game view, and a scaler created inside a test has not run its layout pass, so its scale factor is still 1 and the canvas measures the raw screen: build scratch canvases in **world space with an explicit size**, which pins the space by construction. (2) A flexible-height query **ignores components that are not active in the hierarchy**, so a guard that measures a prefab as authored flags correct hidden branches and misses real violations in them: **activate the whole subtree before you measure.**
5. **Pseudolocalization** *(a proposal)*: lengthening every string and swapping in accented glyphs surfaces the whole fixed-container class in one pass instead of one instance at a time, so it is worth proposing even for a product in one language (I). Localization proper is a separate decision; if it comes, use a real plural and message format instead of concatenation.

**Screenshot comparison and visual regression: a signal, never a gate.** A pixel diff gives false positives from font and anti-aliasing differences between environments, and a comparison by a vision model reduces them without removing them (I). A screenshot is the right instrument for "did this draw at all" (§3), not for "is the hierarchy correct": read the hierarchy for that. And do not let the agent that wrote a check certify the result: that is §4's finding applied to tests.

Still not automatable in the editor: real safe-area and cutout behaviour. `release-hardening.md` says where it can be seen.
