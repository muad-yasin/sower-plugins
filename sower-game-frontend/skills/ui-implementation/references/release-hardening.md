# Release hardening

*Open this file when a release build is being prepared: the device matrix, the build settings, the stripping trap and how to find it without a device, the safe area, and the touch edge cases.*

**Grades.** **Seen** = it happened on the source project, with its record named in `evidence.md`. **D** = documented in a named source, read on the date given. **I** = inferred, with the reason in the sentence.

**Device passes are the owner's to raise.** On the source project its owner ruled on 3 August 2026 that an agent never proposes one, in any form, not even as "a quick check on a real screen" (Seen). Whether that holds for your project is its owner's call. Every item below that needs no device says so.

- **A matrix of three devices** (not checked at a source; stated here since September 2026): one tall flagship with a cutout and a high refresh rate, one budget phone with little memory, and one older device near the minimum supported API. Sweep aspect ratios and cutouts in a device simulator first, and keep the physical phone for performance and the feel of touch, which a simulator cannot give (I).
- **Check the build settings as booleans before any release build** (Unity on Android; adapt the names, keep the shape): AOT compilation, 64-bit ARM, the store's app-bundle format, engine-code stripping on, a managed stripping level chosen on purpose, and the target API level at the store's current floor (I). **Read the floor and its deadline from the store's own current requirements**, never from a skill file: anything written here would be stale when it mattered.
- **One deliberate profiling pass on UI rebuilds, on the device, before launch:** canvas rebuild spikes on persistent HUD elements, any crawling ticker, and the longest list in the product. Editor timings on a development machine say nothing about a budget phone (I). An engine animation component on UI elements dirties them every frame even when nothing changes (not checked at a source; stated here since September 2026): animate from code.
- **The stripping and reflection trap, and the cheap way to find it.** Unity's linker decides what to strip by a static analysis of the code that exists at build time, at a level you configure, and attributes or a link file tell it what to keep (D, Unity 6000.6 manual, "Managed code stripping", read 2026-11-22). A type reached *only* by reflection or by JSON deserialization can therefore be stripped: a crash that exists only in the release build, at the moment the stripped path first runs; save round trips and content loaded indirectly are the shapes at risk (I). First, build a **desktop** AOT development build at the same stripping level and run a startup smoke test through every reflection and deserialization path: it takes minutes on a development machine and needs no device. Then preserve whatever is reached by reflection, and develop at the stripping level you will ship, so the behaviour is no launch-day surprise (I). The source project's release audit of 20 September 2026 found its managed level unset, which it read as Minimal, with no link file, and marked the setting unverified: probably fine, it said, but only a release build run through the purchase and ad paths would prove it. It advised against raising the level before release (Seen).
- **The safe area, and where it can be seen.** Unity's `Screen.safeArea` "Returns the safe area of the screen in pixels", relative to the application window and not the physical screen, and the reference asks you not to place interface elements outside it; on Android 15 and later the application always renders into the cutout, whatever the player setting says, and the safe area excludes it (D, Unity 6000.6 scripting reference, read 2026-11-22). Convert it to anchors on a container under the root canvas, keep background art outside that container so only the interface moves inward, and convert again on an orientation change (I). On the source project the Editor reported no cutout at all, so a safe-area fix of July 2026 was reverted over "no visible change", which the later record calls a false alarm; it says such a fix can be confirmed only on a real device build (Seen). Do not take the Game view as evidence either way.
- **Touch edge cases on the device build** (I): two simultaneous touches on two different buttons (a tap cycle must not fire twice); an incoming call, or the notification shade pulled down mid-hold (`SKILL.md` rule 5's single idempotent reset covers it: verify anyway); the safe area against gesture navigation at the bottom of the screen; and the platform's minimum target size everywhere. Quick manual checks, not a suite.
